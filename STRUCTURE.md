# Before and after

The same five-agent system, drawn twice. Nothing about what the agents *do*
changes between these two diagrams. What changes is where their rules live and
whether anything can take one back out.

---

## Before

```
agents/
  web/       web-agent.md       170 lines
  organic/   organic-agent.md   179
  crm/       crm-agent.md       274
  paid/      paid-agent.md      311
  intel/     intel-agent.md     579
  shared/    note-command.md
  */skills/  20 skills
```

One agent per domain, each declaring its scope, what it does not cover, and a
routing table saying which skill to load for which request. That part was sound
and stayed.

What the audit found underneath it:

**Shared rules lived in five places at once.** `Plan first` appeared in all five
agents under five different hashes. `Workflow` in four, four variants. Three
more sections in three agents each. The structure was identical every time; only
the domain examples differed, which is exactly the case a template solves and
copy-paste does not.

**Three rules had propagated partway.** Present in some agents, missing from
others, with no record of the decision. The clearest one: *verify every path and
ID before asserting it, because plans hallucinate paths.* Four agents had it. The
one that did not is the agent that plans budget changes.

**Nothing could retire a rule.** A search across 6,177 lines for anything that
deprecates, expires or reviews found one match, and it was a note about a
deprecated Google API version. Sixteen rules carried the date they were written.
The oldest was 88 days old and stamped `checked` against a credential path that
had since moved.

**Induction existed, and it was manual.** A `/note` command took a learning and
filed it correctly: corrections to memory, technical recipes to the domain skill,
behavioural changes to the agent file. It is genuinely steps 3 and 4 of the loop,
working. It fires only when a person remembers to type it.

Scored against the seven steps: **04 Route** and **06 Retrieve** solid, **03
Induce** working but human-triggered, and **01, 02, 05, 07** absent.

## After

```
adaptive-agents/
  agents/
    web/web-agent.src.md      domain only: scope, routing, what it does not cover
    web/web-agent.md          GENERATED = src + shared/base.md
    ...
  shared/
    base.md                   every shared rule. one copy.
  skills/
  data/
    raw/                      frozen traces, gitignored
    labeled/                  hand-labelled failure sample
  evals/
    tasks.json
  skillbox/
    proposed/ approved/ rejected/
  scripts/
    snapshot_traces.py  to_episodes.py  audit_structure.py  build_agents.py
  RULES.md
```

What each addition buys, by step:

**01 Capture** is `hooks/record-failure.sh`. It fires on `PostToolUseFailure` and
writes the failure, with its command and output, to `~/.claude/incidents.jsonl`
at the moment it happens. The path is fixed rather than inside this repo because
the hook fires from whatever directory the agent is working in. Transcripts get
deleted by the tool that wrote them, so a log the system owns is the only copy
that survives, and recording at the moment of failure keeps the context that
mining later throws away.

**02 Detect** is `cluster_incidents.py`. It groups the log by the shape of the
failure, so three missing packages with three names read as one wrong
interpreter. Failures the harness flagged and candidates that merely printed
something error-shaped are kept apart, and never added together.

**05 Propagate** is `shared/base.md` plus `build_agents.py`. A rule is written
once and assembled into every agent that needs it. `--check` fails a build when a
generated file has drifted from its source, which is what a pre-commit hook runs.

**07 Measure and prune** is `RULES.md` plus `evals/`. Every rule records the
failure that produced it and when that failure was last seen. A rule whose
failure stopped recurring is a candidate for removal, and the eval tasks are what
you re-run to find out.

**03 Induce** is the `induce-rules` skill. Its trigger moved: instead of firing
when a person remembers to type a command, it reads the clusters. Approval stays
human, because approval is what turns a proposal into behavior every future run
inherits.

## The move that costs nothing and is easy to get wrong

Consolidating a shared rule looks like it should be a reference:

```markdown
## Shared rules
These live in `shared/base.md` and apply always.
```

It is not enough. An agent's own file is in context from the first token; a
referenced file is only read if something decides to read it. A rule you cannot
guarantee was read is a rule you cannot rely on.

So the text is assembled in physically, from one source. The proof that the
refactor is safe is a diff:

```
$ diff backup/web-agent.md web/web-agent.md
6a7,8
> <!-- GENERATED by scripts/build_agents.py from web/web-agent.src.md + shared/base.md.
>      Edit those, not this file: the next build overwrites it. -->
```

One comment, and nothing else. Every rule is byte-for-byte where it was, and
there is now one copy instead of four.

**The banner goes after the frontmatter, never above it.** YAML frontmatter has
to start at line 1. Put a comment above it and the harness stops parsing `name`,
`description` and `tools`, and the agent quietly stops registering. Nothing
raises an error; the agent simply is not there any more.

---

## What the after state does not claim

The audit measures structure. It says a rule exists in five versions and that
nothing can retire one. It does not say the agents produce better work, because
that needs the eval tasks re-run before and after, on traces that did not exist
when this was written.

That is the honest boundary of a structural audit, and it is also the reason
step 01 comes first.
